## Что сейчас реализовано — функционал
- Основной поток: пользователь вводит/ищет предмет в `CalculatorForm`, выбирает количество и перки → нажимает Calculate → `calculateAllResources` возвращает:
  - `base` — итоговые базовые материалы,
  - `intermediate` — промежуточные крафты,
  - `silver` и `xp`.
- Перки влияют на: ресурсосбережение, скидку серебра, бонус XP, yield (эффективный выход).
- `ResultDisplay` показывает:
  - суммарные Silver / XP,
  - древовидный расклад ресурсов (expandable), с возможностью pin/unpin ресурсов,
  - pinned-resources блок (список закреплённых ресурсов).
- Поисковая логика: в `CalculatorForm` есть быстрый поиск с фильтрацией по имени и по первичным ингредиентам, плюс кастомный dropdown.
- Утилиты:
  - `recipeUtils.findRecipesThatUse(item)` уже есть — ищет рецепты, где используется ингредиент.
  - `getCombinedRecipes()` объединяет локальные и API-данные (есть сервис обновлений).
  - `calculateAllResources` поддерживает циклы, мемоизацию, применяет перки.

## Краткое наблюдение по дизайну / UX
- Чёткая двухпанельная логика: форма слева + perks sidebar справа (sidebar скрываемый).
- Результат — читаемая древовидная визуализация с цветовой градацией уровней (`color-0..5`), кнопки pin и раскрытие.
- Форма поиска ориентирована на быстрый выбор и подсказки (autocomplete-like).
- Код CSS организован по компонентам, классы понятные; взаимодействия — простые и предсказуемые.

## План — 1 Реверсивный крафт («берешь primary ingredient и он выдает его крафты»)

Цель: дать пользователю возможность выбрать любой ингредиент (базовый или промежуточный) и увидеть все рецепты, в которых он используется, с возможностью перейти в расчёт для любого найденного рецепта.

Контракт (коротко)
- Ввод: имя ингредиента (string).
- Выход: список рецептов [{ name, quantityRequired, canCraft, craftingLevel, image? }].
- Поведение: показывать только прямые рецепты (опция — рекурсивный поиск «used in chain»).

Подзадачи
1. UI:
   - Добавить кнопку/иконку рядом с полем поиска: «Find recipes that use this ingredient» (или пункт в dropdown: "Show uses").
   - Новый компонент `ReverseCraftPanel.jsx` — компактный список рецептов с возможностью:
     - нажать на рецепт → перейти в форму/прямо выполнить расчёт (prefill CalculatorForm with that recipe as target);
     - показать краткую карточку (level, required qty, thumbnail).
2. Логика:
   - Использовать существующую `recipeUtils.findRecipesThatUse(itemName)` для прямых использований.
   - Добавить опцию «рекурсивный поиск» (findRecipesThatUseRecursively) — если пользователь хочет увидеть все рецепты выше по дереву (опционально).
3. Интеграция:
   - В `CalculatorForm` при выборе в результате «используется в» — автоматический prefill selectedItemName + (optional) amount и вызов calculate.
   - Добавить визуальный переход/фокус (закрыть dropdown, подсветить).
4. Тесты:
   - Unit: `findRecipesThatUse` возвращает корректный набор для sample-data.
   - UI: snapshot тест компонента `ReverseCraftPanel`.
5. Edge cases:
   - Имена ингредиентов неоднозначны — использовать exact match + insensitive search.
   - Отсутствие рецептов → показать «No recipes found».
   - API vs local recipe format (поддержать оба формата — recipeUtils уже делает это).
6. Оценка объёма:
   - Реализация UI + wiring: ~2-4 часа.
   - Доп. рекурсивный поиск и тесты: +1-2 часа.

Файлы для изменения/создания
- Add: `src/components/ReverseCraftPanel.jsx` (UI)
- Edit: CalculatorForm.jsx (добавить кнопку/пункт в dropdown + вызов)
- (опционально) Edit: recipeUtils.js (если нужно расширить рекурсивный поиск)

Критерии приёмки
- При выборе ингредиента и нажатии «Show uses» список отображается и кликабельные элементы запускают расчёт.

## План — 2 Поиск по локациям («выбираешь локацию и он выдает тебе крафты доступные с эксплоринга этой локации»)

Цель: позволить фильтровать/искать рецепты, доступные исходя из набора материалов, добываемых в выбранной локации.

Предположения (если отсутствуют данные)
- Существует `data/location-config.js` или аналог, где для каждой локации есть список доступных дропов и, возможно, их относительная частота.
- Если данных о drop-rate нет — будем опираться на булеву доступность (доступен/не доступен) и позже расширим до вероятностей.

Контракт
- Ввод: выбранная локация (string), опция включать черновые crafted intermediates (bool)
- Выход: список craftable recipes, фильтрованных по тому, можно ли обеспечить все базовые материалы из локации (с учётом цепочек крафта)
- Параметры: опция «только прямые (использует только дропы)» / «рекурсивно (можно использовать крафты из тех же доступных дропа)»

Подзадачи
1. Данные:
   - Проверить/нормализовать `data/location-config.js` (location -> { drops: {item: dropChance}, staminaRates? }).
   - Если нет — предложить формат:
     { "Forest": { drops: { "Twig": 0.5, "Berries": 0.2 }, staminaMultiplier: 1 } }
2. Core алгоритм:
   - Определить замыкание доступных предметов:
     - Начальный набор = все дропы локации.
     - Итеративно: добавить все craftable items, у которых все ингредиенты входят в текущем наборе (т. е. можно скрафтить из имеющихся дропов + ранее добавленных крафтов). Стоп при отсутствии роста — получаем набор всех предметов, доступных «от и до».
   - Результат = все рецепты из `getCombinedRecipes()` у которых item ∈ closure.
3. UI:
   - Добавить селектор локации в `CalculatorForm` (или отдельный `PinnedLocationSelect.jsx` уже есть — использовать/усилить).
   - Показать переключатель: «Direct drop only / Allow crafting chain».
   - Отдельная панель «Available in location» — показывать количество рецептов и список с быстрым переходом в расчёт.
4. Интеграция с поиском:
   - При выборе локации dropdown поиска должен предлагать только те рецепты, что доступны (фильтр).
   - Добавить режим: «Поиск по локациям» — когда вводишь название локации в поле поиска, подсказки рецептов ограничены.
5. Тесты и проверки:
   - Unit: closure algorithm — корректен на contrived graph (cyclic, missing ingredients).
   - Smoke UI: выбрать локацию → список рецептов соответствует ожиданиям.
6. Edge cases:
   - Частично доступные ресурсы (нужны ресурсы из нескольких локаций) — явно пометить «частично доступно».
   - Циклы в рецептах — алгоритм должен избегать бесконечной итерации (стоп по фиксированному набору).
   - Большие графы — сложность O(N*M) но приемлема для dataset размера игры.
7. Оценка объёма:
   - Алгоритм + unit tests: 3-5 часов.
   - UI интеграция и фильтрация поиска: 2-4 часа.

Файлы для изменения/создания
- Edit: CalculatorForm.jsx (location select + filter toggle)
- Add/Edit: PinnedLocationSelect.jsx или `LocationConfigPanel.jsx`
- Edit: recipeUtils.js (add `findRecipesAvailableInLocation(locationName, allowChain=true)`)

Критерии приёмки
- При выборе локации список рецептов/поиск фильтруется корректно; опция chain работает как описано.

## План — 3 Дроп-рейт (вынести функцию из pinned, показывает дроп со всей локации. настройка по стамине/сидру/ап)

Цель: иметь отдельную, повторно используемую службу/утилиту для расчёта ожидаемых дропов по локации с учётом пользовательских параметров (stamina / cider / AP / modifiers), и UI для настройки этих параметров и отображения агрегированного дропа.

Подзадачи
1. Данные:
   - Структура `location-config` должна содержать для каждой локации: список врагов/спотов с вероятностями дропа по предметам, и базовую стоимость/повторение (AP/stamina per attempt).
   - Если в данных сейчас только булевы флаги — добавить/переопределить формат, но сделать backward-compatible.
2. DropRateService:
   - Добавить `src/services/DropRateService.js`:
     - Функция `getExpectedDrops(locationName, {stamina, cider, ap, attempts})`:
       - Рассчитывает количество попыток (attempts) из stamina/AP modifiers (учесть cider если он даёт больше попыток).
       - Для каждого предмета суммирует expected = attempts * perAttemptProbability * yieldModifier.
       - Поддерживает агрегирование по всей локации (сумма по спотам).
     - Экспортировать вспомогательные функции: `calculateAttemptsFromStamina`, `applyModifiers`.
3. UI:
   - Добавить в `LocationConfigPanel` (или новое `LocationDropsPanel.jsx`) контролы:
     - Поле stamina (число), cider toggle/amount, AP per run, custom attempts.
     - Кнопка «Посчитать ожидаемый дроп».
   - Отобразить таблицу: item | expected quantity | percent chance per run | source (spot).
   - Интеграция: в `ResultDisplay` показывать «Available from selected location (expected per X runs)» и кнопку pin -> добавлять в pinned-resources с рассчитанными qty.
4. Вынести логику, которая сейчас, кажется, жёстко привязана к pinned resources, в сервис (DRY).
5. Тесты:
   - Unit: точность расчётов на известных входах.
   - Edge: cider/AP = 0, слишком большие значения (cap attempts), неизвестная локация.
6. Edge cases & UX:
   - Если данные по дропу отсутствуют — показывать объяснение «нет данных по drop rates».
   - Опция «normalize to per-stamina / per-hour».
   - Ограничить выпадающие количества, форматировать числа.
7. Оценка объёма:
   - Реализация сервиса + базовый UI: 4-6 часов.
   - Расширенные опции (normalize, per-hour): +1-2 часа.

Файлы для изменения/создания
- Add: `src/services/DropRateService.js`
- Add/Edit: `src/components/LocationDropsPanel.jsx` (UI)
- Edit: ResultDisplay.jsx (интеграция с pin)
- Edit: `data/location-config.js` (если нужно добавить/нормализовать drop probabilities)

Критерии приёмки
- Можно задать stamina/AP/cider и получить ожидаемое количество дропа по локации; результат можно pin'ить в pinned resources.
